# Investigation record — post-validation review of provenance-core (2026-10-12)

Source: five read-only investigations run after `provenance-core` was validated GO (`.kiro/specs/provenance-core/validation-report.md` §3, items W1–W9), reviewed with the repo owner on 2026-10-12. The owner's governing instruction: **cost and time of work are not a concern; accuracy and scientific credibility supersede them.** Scratch harnesses (`scratchpad/w1`…`w8`) are not persisted; the numbers below are what the specs may rely on. Everything here was measured on HEAD `c21c929` unless marked *reasoning*.

## Cross-cutting findings
- **No real model output exists in the repo or on this machine** (`outputs/` holds only ~200-byte `run.log` files; `manifest.json` holds one stub). Every frequency below that concerns model behaviour is reasoning, not measurement.
- **Cross-invocation resume is dead today (pre-existing).** `RUN_FOLDER_NAME` is `run_<timestamp>` computed at import (`utils/path_utils.py`); `pdf_processor.is_resumed` looks in the new `OUTPUT_DIR`, so a second process never finds the previous output (reproduced: second process re-issued all 15 `extract_chunk` calls although the manifest said `complete`). `cost-and-run-reporting` plans to fix this by persisting the output path; after that, full and partial resume become common.
- **`run_id` identifies a configuration, not an execution.** It is derived from config/schema fingerprints and model ids; two runs of the same config share it, `created_at` is second-granular. `sanitize_extracted_values` / `exported_value_normalizer` (from `load_local_config`) are not in the config fingerprint.
- **`agent_schema.json` `policies`/`extraction_rules` are never sent to the model** (grep: only getters in `agents/validator.py`) and describe a stale contract (`s: not_reported`, `v: null`, integer `c`). The prompt (`prompts.py`) never tells the model what a missing value looks like; `api_client._json_schema_format` makes `v` a string (null impossible), `loc` a required (possibly empty) array, `c` an enum `h|m|l|nr`. `v == "nr"` is only a pipeline convention (`deterministic_merge.NOT_REPORTED_VALUE`, `extraction_report.py`, the prefill).
- `num_chunks=1` raises `ZeroDivisionError` in `_get_domain_to_chunk(1)` at config load (pre-existing); `num_chunks=2` works.

## W1 — "not reported" (`nr`) claims
- The validator accepts `nr`/`nr`/`[]`, `nr`/`h`/`[S1]` (nr with evidence ids), a real value with `c=nr`, empty `v`, and a real value with `c=h` and no `loc`. `nr` value and `nr` confidence are independent.
- Deterministic merge: empty `v` becomes `nr`/`nr`/`[]` (produced without a model call but recorded today as origin `model`, against Req 5.7); a literal `"nr"` is an ordinary string (a chunk answering `nr` against a value is a conflict).
- Today the claim adapter classifies any claim without evidence as `unsupported` (`claim_adapter._classify`), `validation._check_unsupported_claims` warns, and `completeness.check_claims` re-derives the gap from the graph, so **severity overrides do not change completeness** (tested: `unsupported_claim: info` changes the finding, not the state). Only `origin == "prefill"` claims are claim-level-only (decision 4.8).
- With a per-field `nr` probability p, documents reading `complete` of 40: p=0% → 40, 0.5% → 28, 1% → 18, 2% → 10, 5% and above → 0; the run is `incomplete` for any p > 0 (≈ (1-p)^60 per document). A genuinely uncited asserted value is invisible among 10% `nr`.
- Downstream specs already model absence: multiagent-extraction R2.1–2.4 (every non-`nr` value must cite evidence; an `nr` answer should carry the ids where absence was checked: verified vs unverified absence), agreement-statistics 1.3 (`nr` is an explicit rating), evaluation-harness 3.3 (unsupported-answer rate over *asserted* values), reviewer-ui 4.4 (human "mark not reported").
- Prototype of the chosen design (typed `answer` field + `unverified_absence` info finding + claim-level `complete`): 3-document run reads `complete`; a real uncited value among 10% `nr` still flips its document; the HEAD reader reads the new artifact (key lands in `x-compat-unknown`).

## W2 — scale
- Measured with the real `orchestrator.run_pipeline` (only GROBID/OpenAI/tokenizer stubbed), mixed TEI fixtures, ~309 evidence nodes/document: nodes 114k / edges 176k at N=300; artifact 0.67 MB/document (11.4× the extraction JSON), gzip 22× smaller; whole run off→on 47 s→105 s at N=300; `snapshot()` calls total 28.5 s at N=300 (fit N^2.03; ≈5.3 min projected at 1000); RSS delta 4.3 MB/document (1298 MB at N=300).
- **The memory peak is the end-of-run serialization** (`json.dumps(indent=2)` pure-Python encoder: 4.3× the output; `_encode_artifact` transient 360 MB at N=100), not the recorder (retained store 0.39 MB/document; run-end transient 3.85 MB/document). Failure mode at ≥~1000 documents: OOM **kill after all extraction**; per-document outputs/manifest survive, run-level provenance is lost, and a rerun treats finished documents as resumed so provenance is never regenerated. A Python `MemoryError` degrades gracefully (verified with `ulimit -v`).
- Prototype of recorder accessors + streaming writer: output **byte-identical**, RSS delta at N=300 1298 → 234 MB, tracemalloc peak 360 → 10.7 MB at N=100, `snapshot()` 28.5 s → 0.2 s. Streaming conflicts with 5 serialization tests that encode the "encode fully before touching the filesystem; name the path; create no directory" write contract.
- Artifact bytes (30 docs): evidence nodes 50%, edges 36.3% (`belongs_to_source` 24.3%), claims 7.6%; `src:<64hex>` strings are 31.5% of all bytes. Lossless cuts (dropping structural edges/defaults, interning) reach −50% to −74%; **rejected by the owner** (explicit edges and un-elided records are more self-describing, Req 7.3; elision adds reader-inconsistency risk). Cited-only evidence (−54%) contradicts Req 4.1/8.3 and breaks evidence-routing/reviewer-ui. **Both rejected.**
- Expected corpus: 20–500 documents typical, up to a couple of thousand at the edge (product.md; corpus-and-schema-builder "500-file batch", "hundreds to low thousands").

## W3 — enabled vs disabled; reference-only exhaustion
- Reproduced: provenance on retains the output (unknown id stays in `location`, critical `dangling_reference`, manifest `complete`); off fails the document (`failed_chunks`/`failed_chunk_5`, no output). Repair call counts identical. Retained documents are invisible outside the provenance artifact (CSV has only `field_name`/`extracted_value`; `flagged_fields.csv` flags only `l`/`nr` confidence; manifest bare `complete`); and the critical finding does not move completeness.
- Only unknown ids (incl. case/whitespace variants) reach exhaustion; duplicates are accepted by strict validation and only reported.
- **`valid_location_ids` is the FULL evidence map while the model sees only `select_paper_evidence(max_items=150, max_chars=30000)`** (further pruned per call by `_check_and_mitigate_budget`): ids never shown on the three fixtures at defaults: arXiv 79%, PLOS 41%, bioRxiv 18%. A guessed id that exists but was never shown passes silently under every option; pruned-but-valid ids can never trigger the unknown path.
- Removing the retain path breaks 8 tests (1 in `test_repair_retry_provenance.py`, 7 in `test_process_pdf_provenance.py`); `test_the_same_input_without_provenance_still_fails_exactly_as_before` still passes. A synthesis failure reason carries only `str(exc)` ("RepairExhaustedError … attempts=2"); the ids are in `exc.metadata["last_error"]`.

## W4 — critical findings do not degrade completeness
- `compute_completeness` never reads `findings` (only `report.completed`); only `unsupported`/`missing_anchor` affect it indirectly through claim support computed from the graph. Findings that never affect completeness: `graph_cycle`, `dangling_reference` with a second valid citation, `source_not_represented`, `evidence_out_of_run_context`, `inconsistent_derivation`, `privacy_carrier_invalid`, `duplicate_identity` (error), `ambiguous_reference`, `duplicate_reference`, `orphan_node`. Measured: an injected derivation cycle left documents `complete` with a critical `graph_cycle`.
- `invalid_identifier` (critical, `node_id=None`, details only `source_id`/position/truncated item id) is unreachable from current code (ids are `S/T/F%06d` or the reserved `M-*`); reachable only through a tampered evidence cache (no integrity check on the cache file). No requirement says completeness reflects findings; Req 2's objective ("an incomplete trace never mistaken for validated evidence") and the design's Error Strategy argue for it.

## W5 — empty / resumed runs
- `start_run_provenance` returns None for an empty plan; `run_identity_from_identities` refuses empty input. A hand-built `RunIdentity` with `document_fingerprints={}` goes through the whole run-end sequence with no `src/provenance` change (1.2 KB artifact, run `undetermined`). Marking resumed documents inside `document_fingerprints` does not work (completeness enumerates documents from that mapping → `undetermined`); a marker is a new run-level key (schema change).
- With a reused run folder: a fully resumed run leaves the old artifact looking like the new run's; a partially resumed run's artifact lists only the processed documents and overwrites the earlier artifact, with an identical `run_id`.

## W6 — stage status is not serialized
- The artifact keys are `schema_id, schema_version, run, nodes, edges, missing_segments, validation, completeness`. Not recoverable from it: which stages are `complete`, which `not_run`, `STAGE_CONTRACTS` (so Req 7.3 "interpretable without pipeline internals" is only partly met), multi-valued per-document failure reasons (flattened into segment text), chain-validation status beyond `validation.completed`.
- `not_run` stages are never reported missing (policy 4.5). Its justifications cannot occur in production: `num_chunks=1` crashes at config load; the synthesis skip is unreachable with the shipped extraction map (domain 13 gives the synthesis chunk its own fields). Today `not_run` follows only an upstream failure; the risk is a future integration forgetting a mark and silently reading `complete`.
- An old reader drops an unknown top-level key with one WARNING; a read-then-write loses it. 1.0.0 is unconsumed (pushed 2026-10-11; no real artifacts exist; audit-export/reviewer-ui not implemented).

## W8 — privacy carrier attach path
- Timing: labels are per document at ingest (privacy-core tasks 5.3); decisions come later inside `process_pdf` after the evidence package is built (`DisclosureGate.evaluate(label, artifact_ids, now)`, privacy-core design L831); evidence nodes are recorded earlier inside `build_or_load_evidence_bundle`; the **ValidationRecord is created inside `graph.attach_validation` at run end** (`graph.py` `privacy=UNKNOWN_PRIVACY`) and never passes through the recorder or any adapter. A `dataclasses.replace(node, privacy=…)` before recording works and round-trips; re-recording with a different carrier keeps the first and appends `duplicate_identity` (error; value-insensitive dedupe key; completeness stays `complete`).
- public-private-provenance requires one disposition per graph node and `child_more_permissive_than_source` (needs a decision on the SourceNode); privacy-core defines carriers only for source and evidence ids; claim/derivation/validation nodes get no carrier in any spec; the carrier has one `decision` string and no `decision_id`, so a node cannot be tied back to the privacy audit record and decisions are per packet while a document may have several packets. audit-export hashes the written artifact files and reads `node.privacy`; a post-hoc enrichment pass would invalidate those digests and cannot recompute completeness (stage status is not serialized).
- Prototype of `attach_carriers(graph, mapping)` (~12 lines in `graph.py`): 1615 existing provenance + dependency-direction tests pass including the 9.4 inertness and import-isolation guards.
